**機能ID**: 006-mcp-knowledge-system
**状態**: ドラフト
**作成日**: 2025-10-27
**種別**: PoC（概念実証）
**対象フェーズ**: Phase 1-3（3-4週間）

## エグゼクティブサマリー

### 目的

AIエージェントとの対話中に生成される知識を自動的に捕捉、構造化し、検索可能にすることで、組織的学習を可能にする。知識は通常の業務活動の副産物として蓄積され、ユーザーによる手動のドキュメント作成作業を不要とする。

### 課題

組織が貴重な知識を失う状況：
- 問題解決中に得られた教訓が文書化されない
- 試行錯誤を通じて発見されたベストプラクティスが消失する
- 繰り返し発生する問題の解決策が毎回再発明される
- チームの専門知識が個人の経験として孤立したままになる

手動の知識管理は、ドキュメント作成に時間がかかり、時間的プレッシャーの下でしばしば無視されるため失敗する。

### 価値提案

- **ゼロエフォート捕捉**: AIエージェント利用中に知識が自動的に蓄積
- **インテリジェント発見**: 類似状況に直面したときに関連する過去の経験を発見
- **チーム学習**: 個人の発見が自動的にチーム全体の利益となる

### 成功基準

1. **捕捉率**: 適格なAI対話の80%が、ユーザーの介入なしに知識カードとして記録される
2. **発見速度**: ユーザーがクエリから3秒以内に関連知識を発見できる
3. **関連性**: クエリの60%で、上位10件の検索結果に少なくとも1つの直接適用可能な知識カードが含まれる

## スコープ

### スコープ内

**コア機能**:
- AIエージェント対話からの知識の自動捕捉
- 教訓、ガイドライン、落とし穴、ケーススタディ、FAQの構造化保存
- 多手法検索（意味、キーワード、関係性）
- 2層アクセス制御（個人知識とチーム知識）

**PoC境界**:
- ローカルデプロイメントでのデモンストレーション
- チームレベルの知識共有のみ
- 基本的なプライバシー保護（PII マスク）
- 必須の監視とログ記録
- 知識関係の手動承認

### スコープ外

**明示的に除外**:
- 組織全体または複数部門の階層（個人/チームを超えるもの）
- 細かいロールベースのアクセス制御
- 高度な知識グラフトラバーサル（1-hop接続に限定）
- 本番級のセキュリティとコンプライアンス機能
- リアルタイム監視ダッシュボード
- 知識の編集または削除機能
- 多言語翻訳
- 外部ナレッジベースとの統合

### 前提条件

1. **環境**: システムは管理されたローカル/オンプレミス環境で動作
2. **ユーザー**: すべてのユーザーはAIエージェント対話の基本的な知識を持つ
3. **コンテンツ**: 知識は主に日本語のテキストベース
4. **スケール**: PoCでは最大10-20の同時ユーザーをサポート
5. **データ**: チームサイズは1チームあたり3-10名
6. **プライバシー**: PoCには基本的なPIIマスクで十分（GDPR準拠ではない）

## ユーザーシナリオ

### 主要アクター

1. **知識作成者**: 業務タスクにAIエージェントを使用するチームメンバー（暗黙的役割）
2. **知識探索者**: 関連する過去の経験を検索するチームメンバー
3. **システム管理者**: PoCデプロイメントと設定を管理する人

### コアユーザーフロー

#### シナリオ1: 自動知識捕捉（ゼロエフォート作成）

**アクター**: 知識作成者（ユキ、ソフトウェア開発者）

**コンテキスト**: ユキはパフォーマンス問題のトラブルシューティングにAIエージェントを使用している

**フロー**:
1. ユキがAIエージェントに問題を説明: 「APIの応答時間が突然5秒に増加した」
2. 会話を通じて、AIエージェントが根本原因を特定するのを支援: データベースインデックスの欠落
3. ユキがソリューションを実装し、動作を確認: 応答時間が200msに低下
4. **システムが自動検出**: 明確な問題-解決-結果パターンでのタスク完了
5. **システムが評価**: コンテンツが品質閾値を満たす（長さ、具体性、重複なし）
6. **システムが作成**: 「データベースインデックス欠落によるAPI応答遅延」というタイトルの知識カード
7. **システムがログ**: 監査証跡用の構造化記録
8. **ユキが確認**: 中断なし - 知識はバックグラウンドで静かに捕捉される

**期待される結果**: ユキが明示的なドキュメント作成アクションを取ることなく、構造化フィールド（situation、action、outcome、applicability）を持つ知識カードが存在する。

**受入基準**:
- [x] システムがタスク完了イベントを検出
- [x] システムが会話から構造化情報（situation、action、outcome）を抽出
- [x] システムが品質を検証（≥400文字または≥3見出し、≥5%具体的詳細）
- [x] システムが重複を防止（7日以内の同じコンテンツをチェック）
- [x] システムが保存前にPIIをマスク（メール、電話番号、社員ID）
- [x] システムが1日の制限を尊重（≤1ユーザーあたり1日3カード）
- [x] システムがメタデータを含む捕捉イベントをログ
- [x] プロセス全体が2秒以内に完了

#### シナリオ2: チーム知識の進化

**アクター**: 複数のチームメンバー

**コンテキスト**: 3人の開発者が独立して類似のパフォーマンス最適化技術を発見する

**フロー**:
1. **1週目**: ユキがインデックス最適化で遅いクエリを解決（個人知識が捕捉される）
2. **2週目**: メイがページネーションによりメモリ使用量を削減することを発見（個人知識が捕捉される）
3. **3週目**: タケシが両方の技術を組み合わせる（個人知識が捕捉される）
4. **システム分析**: 3人のチームメンバーのカード間で高い類似性（>0.75）を検出
5. **システムが作成**: 統合されたチーム知識カード「データベースパフォーマンス最適化パターン」を自動生成
6. **将来のクエリ**: すべてのチームメンバーが統合されたガイダンスを確認

**期待される結果**: 個人の発見が手動の統合作業なしにチーム全体のベストプラクティスに収束する。

**受入基準**:
- [x] システムがチームメンバー間の類似個人知識を検出
- [x] システムがパターンを識別（≥3貢献者、≥50%チームカバレッジ、≥0.75類似性）
- [x] システムがチーム知識を自動作成
- [x] チーム知識がチーム全体の検索に表示される
- [x] 元の個人知識がアクセス可能のまま残る

## 機能要件

### FR-1: 自動知識捕捉

**説明**: システムはユーザーの介入なしにAIエージェント対話から知識を捕捉する

**要件**:

FR-1.1: システムはAIエージェント対話イベントを監視する：
- タスク完了イベント
- エラー解決イベント（失敗→成功の結果）
- ドキュメント/設計の確定イベント
- 知識再利用イベント（既存の知識が参照されたとき）

FR-1.2: システムは対話から構造化情報を抽出する：
- タイトル: 状況/解決策の簡潔な要約
- タイプ: lesson、guideline、pitfall、case-study、またはfaq
- 状況: コンテキストと問題の説明
- アクション: 取られたステップまたは使用されたアプローチ
- 結果: 達成された成果
- 適用性: この知識が適用される条件
- タグ: 関連する技術/ドメインキーワード

FR-1.3: システムは捕捉資格を検証する：
- コンテンツ長 ≥400文字 OR ≥3構造化セクション
- 具体的詳細密度 ≥5%（固有名詞、数値、具体的用語）
- 7日以内に重複なし（コンテンツ類似性に基づく）
- 機密キーワードなし（設定可能なブロックリストから）
- ユーザーが1日の制限を超えていない（デフォルト: 3カード/日）

FR-1.4: システムはプライバシー保護を適用する：
- メールアドレス、電話番号、郵便住所、社員IDをマスク
- パターンマッチングと辞書ベースの検出を使用
- マスク後に元のテキストは保存されない

FR-1.5: システムはデフォルトのメタデータを割り当てる：
- スコープ: team（自動捕捉知識のデフォルト）
- 可視性: restricted（公開ではない）
- 所有者: AI対話をトリガーしたユーザー
- タイムスタンプ: 作成日時
- ソース: AIエージェント対話ログの参照

**受入シナリオ**:
- ≥400文字のコンテキストで問題を解決するAI対話が与えられたとき、対話が完了したら、2秒以内に知識カードが作成される
- 今日知識カードが捕捉されたとき、7日以内に同じコンテンツが再度送信されたら、システムは重複作成をスキップする
- ユーザーが今日3枚のカードを作成したとき、別の適格な対話が発生したら、明日まで追加のカードは作成されない
- コンテンツに「tanaka@example.com」が含まれているとき、知識が保存されたら、メールは「[EMAIL]」としてマスクされる

### FR-2: ハイブリッド検索

**説明**: システムは複数の補完的手法を使用して関連知識を発見する

**要件**:

FR-2.1: システムは2つの方法を同時に使用して検索する：
- セマンティック検索: ベクトル類似性を使用した意味ベースのマッチング
- キーワード検索: 全文検索を使用したテキストマッチング

FR-2.2: システムは検索フィルタを適用する：
- スコープ: personal（ユーザー自身）and/or team
- タイプ: lesson、guideline、pitfall、case-study、faq
- タグ: 技術/ドメインキーワード
- 可視性: Publicまたはrestricted
- 言語: ロケールベースのフィルタリング

FR-2.3: システムは複合スコアで結果をランク付けする：
- 類似性スコア（デフォルト重み: 0.6）
- 適用性一致（デフォルト重み: 0.4）

FR-2.4: システムは表示閾値を適用する：
- スコア<0.4の結果を非表示
- スコア0.4-0.6の結果を「低信頼度」としてマーク
- スコア≥0.6の結果を通常表示

FR-2.5: システムは性能目標内で検索結果を返す：
- 初回クエリ（コールドスタート）: ≤1.5秒（p95）
- キャッシュされたクエリ: ≤0.8秒（p95）
- 同時クエリ: 10並列検索をサポート

**受入シナリオ**:
- クエリ「データベースパフォーマンスを最適化する方法」が与えられたとき、検索が実行されたら、結果にインデックス作成、キャッシング、クエリ最適化に関するカードが1.5秒以内に含まれる
- フィルタscope=teamで検索が与えられたとき、結果が返されたら、他のユーザーの個人知識は表示されない
- スコア[0.85、0.72、0.55、0.35]の知識カードが与えられたとき、表示されたら、最初の3枚のカードのみが表示される（0.35は閾値未満）

### FR-3: 構造化ログとトレーサビリティ

**説明**: システムは分析とデバッグのためにすべての操作を記録する

**要件**:

FR-3.1: システムはすべての操作を構造化形式（JSON Lines）でログに記録する：
- タイムスタンプ（ISO 8601）
- リクエストID（操作ごとに一意）
- アクターID（ユーザー識別子）
- 操作タイプ（store、search、promote等）
- 期間（ミリ秒）
- 結果（成功/失敗）
- メタデータ（使用されたモデル、設定値、コンテンツハッシュ）

FR-3.2: システムは再現性を保証する：
- 埋め込みモデル名とバージョンをログに記録
- 埋め込み次元をログに記録
- 検索重み（similarity、fit、support、contradiction）をログに記録
- 重複排除用のコンテンツハッシュをログに記録
- 自動捕捉フラグ（自動vs手動）をログに記録

FR-3.3: システムはログを永続ストレージに書き込む：
- 構造化ログファイル（JSON Lines形式）
- ローテーションポリシー（毎日またはサイズベース）
- 保持期間（PoCには最低30日）

FR-3.4: システムはリクエストトレースを提供する：
- すべての関連ログエントリで一貫したリクエストID
- 捕捉からストレージまでのフルフローをトレース可能
- 検索クエリから結果までをトレース可能

**受入シナリオ**:
- 任意の知識捕捉操作が与えられたとき、操作が完了したら、すべての必須フィールドを持つ構造化ログエントリが存在する
- ログエントリからリクエストIDが与えられたとき、ログを検索したら、すべての関連操作が同じリクエストIDで見つかる
- 100の操作のログエントリが与えられたとき、分析したら、すべてのエントリにembedding_model、embedding_dim、content_hashフィールドが含まれる

|------|------|----------|
| 自動捕捉率 | ≥80% | （自動捕捉カード/適格対話）× 100 |
| 必須フィールド完全性 | ≥95% | （すべての必須フィールドを持つカード/総カード）× 100 |
| 知識タイプ精度 | F1 ≥0.8 | 50枚のカードを手動アノテーション、F1スコアを計算 |
| 検索Recall@10 | ≥0.6 | （上位10件の関連カード/総関連カード）× 100 |
| 初回検索応答時間（p95） | ≤1.5s | コールドスタート検索期間の95パーセンタイル |
| キャッシュ検索応答時間（p95） | ≤0.8s | ウォームキャッシュ検索期間の95パーセンタイル |
| 埋め込みキャッシュヒット率 | ≥70% | （キャッシュヒット/総埋め込みリクエスト）× 100 |
| 同時ユーザーサポート | 10ユーザー | 10の同時検索下でシステムが応答性を維持 |
| 1日の捕捉制限コンプライアンス | 100% | 設定された制限（デフォルト: 3/日）を超えるユーザーなし |

### 定性的成果

**ユーザーエクスペリエンス**:
- ユーザーはワークフローを中断することなく知識を発見
- 検索は応答性が高く、関連結果を迅速に返す
- 知識カードは深いコンテキストなしで理解可能

**チーム学習**:
- 個人の発見が数日以内に他のチームメンバーに利益をもたらす
- 繰り返し発生する問題が知識再利用を通じてより速く解決される
- チームは一貫したタグ付けを通じて共有語彙を開発

**システム信頼性**:
- PoC期間中のデータ損失なし
- コンポーネント障害時の適切な劣化
- トラブルシューティングを導く明確なエラーメッセージ

## 主要エンティティ

### 知識カード

**説明**: 捕捉された知識の構造化表現

**属性**:
- **ID**: 一意識別子、バージョン番号、作成タイムスタンプ、最終更新タイムスタンプ
- **コンテンツ**: タイトル、タイプ（lesson/guideline/pitfall/case-study/faq）、状況、アクション、結果、根拠（オプション）
- **コンテキスト**: 適用性条件（配列）、非適用性条件（配列）、タグ（配列）、証拠ソース（配列）
- **アクセス制御**: スコープ（personal/team/org）、可視性（public/restricted）、所有者ID
- **検索**: 検索可能テキスト表現、セマンティックベクトル、コンテンツハッシュ（重複排除用）
- **メタデータ**: 言語ロケール、使用された埋め込みモデル、埋め込み次元

**関係**:
- 所有者: ユーザー（作成者）
- サポート: 他の知識カード（確認済みまたは候補）
- 所属: チームまたは個人スコープ

**ライフサイクル**:
1. 作成（自動または手動）
2. 検索用にインデックス化
3. 類似知識にリンク（候補）
4. 検索結果で参照
5. 新しい証拠で更新（バージョンインクリメント）

### ユーザー

**説明**: 知識システムを使用する個人

**属性**:
- ユーザーID、名前、チーム所属、役割（作成者/探索者/管理者）
- 1日の捕捉カウント、作成された総カード、最終活動タイムスタンプ

**関係**:
- メンバー: チーム
- 作成者: 知識カード
- 探索者: 知識

### チーム

**説明**: 知識を共有するユーザーのグループ

**属性**:
- チームID、チーム名、メンバー数

**関係**:
- 含む: ユーザー
- 所有: チームスコープ知識カード

## 非機能要件

### 性能

**NFR-1**: システムは劣化なしで10の同時検索を処理する（応答時間<2xベースライン）

**NFR-2**: 初回検索は≤1.5秒（p95）で完了する

**NFR-3**: キャッシュされた検索は≤0.8秒（p95）で完了する

**NFR-4**: 知識捕捉は≤2秒（p95）で完了する

**NFR-5**: システムは最低100の知識カードをサポートし、それを超える場合は適切な劣化

### 信頼性

**NFR-6**: システムはデバッグと分析のためにすべての操作をログに記録する

**NFR-7**: システムは個々のコンポーネント障害（埋め込みサービス、データベース）を適切な劣化で生き残る

**NFR-8**: システムは重複知識作成を防止する（7日以内の同じコンテンツ）

**NFR-9**: システムはデータ一貫性を維持する（部分書き込みなし）

### ユーザビリティ

**NFR-10**: 知識捕捉はユーザーの認識なしに透過的に発生する

**NFR-11**: 検索結果は完全な知識カードを読まずに理解可能（良いタイトル/要約）

**NFR-12**: システムは標準的な日本語を使用する（技術的に必要でない限り専門用語なし）

### セキュリティとプライバシー

**NFR-13**: システムは保存前にPIIをマスクする（メール、電話番号、住所、社員ID）

**NFR-14**: システムはアクセス制御を実施する（個人対チームスコープ）

**NFR-15**: システムは知識作成をレート制限する（デフォルトでユーザーあたり1日最大3カード）

**NFR-16**: システムは機密キーワードを含む知識をブロックする（設定可能なブロックリスト）

### 保守性

**NFR-17**: すべての設定値は外部化される（環境変数）

**NFR-18**: システムログにはトラブルシューティングに十分なコンテキストが含まれる（リクエストID、タイムスタンプ、結果）

**NFR-19**: システムは自動分析用の構造化ログ（JSON形式）を提供する

## テスト戦略

### 受入テストシナリオ

**テスト1: 自動捕捉エンドツーエンド**
1. 品質閾値を満たすAIエージェント対話をトリガー
2. 2秒以内に知識カードが作成されることを検証
3. すべての必須フィールドが入力されていることを検証
4. PIIがマスクされていることを検証
5. 構造化ログエントリが存在することを検証

**テスト2: 重複防止**
1. 対話Aから知識カードを作成
2. 7日以内に同一カードの作成を試みる
3. システムが重複をスキップすることを検証
4. 8日待つ
5. 同一カードの作成を再度試みる
6. システムが新しいカードを作成することを検証（時間閾値が経過）

**テスト3: 検索関連性**
1. 異なるトピックにわたる20の知識カードでシステムをシード
2. 既知の関連カードを持つ10のテストクエリを実行
3. Recall@10 ≥ 0.6を検証（6+クエリが上位10件に関連カードを返す）
4. 検索が1.5秒以内に完了することを検証

**テスト4: 1日の制限実施**
1. 1日にユーザーAの3つの適格AI対話をトリガー
2. 3枚のカードが作成されたことを検証
3. 4番目の適格対話をトリガー
4. 4番目のカードが作成されていないことを検証
5. ログエントリが制限に達したことを示すことを検証

**テスト5: チーム知識進化**
1. 異なるチームメンバーから3つの類似個人知識カードを作成
2. システムが類似性を検出する（≥0.75）ことを検証
3. システムが候補チーム知識を作成することを検証
4. 管理者がレビューし昇格
5. チーム全体の検索が昇格した知識を返すことを検証
6. 元の個人知識がアクセス可能なままであることを検証

### 性能テストシナリオ

**負荷テスト1: 同時検索**
- 10の同時ユーザーが検索を実行
- 各々の応答時間を測定
- p95 ≤ 2秒を検証（負荷下で2倍の劣化を許容）

**負荷テスト2: キャッシュ有効性**
- 同じ検索を100回実行
- キャッシュヒット率を測定
- ≥70%キャッシュヒットを検証
- キャッシュされた応答時間≤0.8秒（p95）を検証

**ストレステスト1: 急速捕捉**
- 1分間に50の知識捕捉をトリガー
- すべてが正常に完了することを検証
- 重複が作成されていないことを検証
- すべての操作の構造化ログを検証

### エッジケーステスト

**エッジケース1**: 最小コンテンツの知識（正確に400文字）
- システムが正しく受け入れて処理することを検証

**エッジケース2**: すべてのPIIタイプを持つ知識（メール、電話、住所、社員ID）
- すべてのPIIパターンがマスクされることを検証
- マスク後もカードが意味を持つことを検証

**エッジケース3**: 一致する知識のない検索クエリ
- 空の結果が適切に返されることを検証
- 応答時間が閾値内であることを検証
- 構造化ログエントリが存在することを検証

## デプロイメント考慮事項

### 環境要件

**PoC環境**:
- ローカルまたはオンプレミスデプロイメント
- 管理されたネットワーク環境（公共インターネット不要）
- 10-20の同時ユーザーをサポート
- PoC期間中24/7利用可能（3-4週間）

### 運用制約

**構成管理**:
- すべての調整可能なパラメータは環境変数を介してアクセス可能
- 閾値、重み、または制限のハードコード値なし
- 構成変更はコード再デプロイを必要としない

**監視要件**:
- 分析用の構造化ログ集約
- 基本的なヘルスチェックエンドポイント（システムアップ/ダウン）
- パフォーマンスメトリクス収集（応答時間、キャッシュヒット率）

**バックアップとリカバリ**:
- JSON形式での1日ごとの知識カードエクスポート
- 1時間以内にエクスポートから復元する能力
- PoC期間+30日間のエクスポート保持

### スケーリング考慮事項（将来）

**PoCの既知の制限**:
- 単一インスタンスデプロイメント（水平スケーリングなし）
- インメモリキャッシング（分散キャッシュなし）
- 1-hopグラフトラバーサルのみ
- リアルタイムインデックス更新なし（定期的な更新は許容）

**将来のスケーリングパス**（PoCのスコープ外）:
- 分散キャッシング層
- マルチホップグラフトラバーサル
- リアルタイムストリーミングインデックス化
- 検索インフラの水平スケーリング

## リスクと緩和策

### 高リスク

**リスク1: 低捕捉品質**
- **説明**: 自動捕捉された知識に十分なコンテキストまたは明確さがない
- **影響**: ユーザーが捕捉された知識を信頼または使用しない
- **可能性**: 中
- **緩和策**: 厳格な品質閾値（≥400文字、≥5%具体的詳細）、チーム知識の人間検証

**リスク2: 検索非関連性**
- **説明**: 検索があまりにも多くの非関連結果を返す
- **影響**: ユーザーが検索を放棄し、手動方法に戻る
- **可能性**: 中
- **緩和策**: 多手法検索（セマンティック+キーワード）、表示閾値（スコア<0.4を非表示）、重みの反復調整

### 中リスク

**リスク3: 性能劣化**
- **説明**: より多くの知識カードでシステムが遅くなる
- **影響**: ユーザーが不満を経験し、システムを放棄する
- **可能性**: 中
- **緩和策**: 100/500/1000カードでの性能ベンチマーク、キャッシング戦略、インデックス最適化

**リスク4: PII漏洩**
- **説明**: PIIマスクがすべての機密情報をキャッチできない
- **影響**: プライバシーの懸念、潜在的なコンプライアンス問題
- **可能性**: 低
- **緩和策**: 複数の検出方法（パターン+辞書）、サンプルカードの手動レビュー、PoCスコープが露出を制限

### 低リスク

**リスク5: 1日の制限が制限的すぎる**
- **説明**: 3カード/日の制限が正当な知識捕捉を妨げる
- **影響**: 貴重な知識が失われる
- **可能性**: 低
- **緩和策**: 設定可能な制限（環境変数）、制限到達イベントの監視

## 制約

### 技術的制約

1. **ローカルデプロイメント**: システムは外部API依存なしで動作する必要がある（オンプレミス埋め込みモデル）
2. **日本語**: 主要言語は日本語、多言語サポートは不要
3. **PoCスコープ**: 実装は概念実証に焦点を当て、本番強化ではない
4. **1-hopグラフ**: 関係トラバーサルは直接接続のみに限定
5. **手動関係**: サポート関係には人間の確認が必要

### ビジネス制約

1. **タイムライン**: 完全なPoCに3-4週間（Phase 1-3）
2. **チームサイズ**: チームあたり3-10名
3. **ユーザー数**: 最大10-20の同時ユーザー
4. **予算**: PoC適切なインフラ（エンタープライズグレードシステムなし）

### 規制的制約

1. **プライバシー**: 基本的なPII保護が必要だが、PoCには完全なGDPRコンプライアンスは不要
2. **データ保持**: PoC期間を超える法的要件なし
3. **アクセス制御**: チームレベルのアクセス制御で十分（細かいRBACなし）
